# Вставка в запомненное поле: обходы и замеры (12.11.2026)

## Суть
- Текст встаёт в поле, где был курсор при нажатии хоткея, даже если человек ушёл в другое окно. Выключатель — `paste.remember_field` (по умолчанию включён); игры — `paste.games`.
- Классическое поле (Блокнот Windows 11, WinForms, Edit/RichEdit) — `EM_REPLACESEL` прямо в каретку, фокус не трогается: 8 из 8 вживую + 3 из 3 сквозных.
- Остальное (Chrome, Electron) — перескок: окно вперёд → проверка, что фокус на том самом поле → Ctrl+V → фокус обратно. Перескок **31–80 мс** (медиана 37–61), вставка 20 из 20 подряд.
- Foreground lock (запрет фоновому процессу ставить окно вперёд) обходит пустое событие мыши через `SendInput` (приём PowerToys): сработало во всех попытках; запасные приёмы не понадобились ни разу.
- Окно или поле пропало, игра, человек печатает без паузы → не вставляем никуда, уведомление «что не так → что сделать», текст ждёт «вставить последнее».
- Повторить замеры: `cargo run --release --example focus_probe -- <сценарий> [раундов]` (`examples/focus_probe.rs`).

## Как устроено
```
хоткей ─► снимок Win32 (поток контроллера, 46–192 мкс): переднее окно, поле в фокусе (GetGUIThreadInfo), exe, полный экран
       └► снимок UIA (поток снимка): элемент в фокусе — AutomationId, имя, тип, рамка, сам элемент
распознано ─► поток доставки:
   1. фокус на том же поле (UIA CompareElements, без UIA — HWND поля)        → обычная вставка
   2. поле — Edit/RichEdit/WinForms                                          → EM_REPLACESEL, фокус не тронут
   3. запомненное окно — игра, или впереди сейчас игра                       → не вставлять
   4. пауза в печати человека 200 мс → буфер готов → окно вперёд → фокус на поле проверен → Ctrl+V
      → приложение прочитало буфер → клавиши отпущены → фокус человеку        → «перескок»
   5. окна/поля нет, фокус на поле не встал                                  → не вставлять, уведомление
```
- Ctrl+V уходит только после проверки, что фокус на запомненном поле: иначе текст попал бы в чужое поле.
- Пока идёт новая запись, доставка ждёт её конца: фокус во время диктовки не трогаем.
- Доставки идут по одной (фокус и буфер обмена у системы одни).
- Код: `src/target/mod.rs` (выбор способа), `src/target/win.rs` (Win32), `src/target/uia.rs` (UI Automation), `src/paste.rs` (вставка «на взводе»).

## Foreground lock: окно вперёд из фона
- **Что:** `SetForegroundWindow` из фонового процесса Windows выполняет, только если процесс «получил последний ввод», подключён к потоку переднего окна или выполнено другое условие из документации; иначе кнопка окна просто мигает в панели задач.
- **Источники:** [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) (список условий); PowerToys `WindowHelpers.BringToForeground` — пустое событие мыши через `SendInput`, затем `SetForegroundWindow`, запасной — `AttachThreadInput` ([WindowHelpers.cs](https://github.com/microsoft/PowerToys/blob/main/src/common/ManagedCommon/WindowHelpers.cs)); AutoHotkey `SetForegroundWindowEx` — `AttachThreadInput` к потоку переднего окна, отпускание Alt, которое глотает свой хук, и двойной Alt в крайнем случае ([window.cpp](https://github.com/AutoHotkey/AutoHotkey/blob/v2.0/source/window.cpp)).
- **Как в Verba** (`win::bring_to_front`): свёрнутое окно сначала разворачивается → пустое событие мыши (без движения и кнопок) + `SetForegroundWindow` → не встало за 60 мс — `AttachThreadInput` к потоку переднего окна → не встало — отпускание Alt с меткой `SWALLOWED_MARK`, которую наш хук глотает (система ввод видит, приложения — нет). К зависшему окну (`IsHungAppWindow`) не подключаемся: `AttachThreadInput` к нему может повесить поток.
- **Проверено:** окно встаёт первым приёмом во всех попытках: 20 из 20 подряд на `contenteditable` в Chrome, плюс 30+ раундов в других сценариях; встаёт за 2–3 мс. `AttachThreadInput` и Alt-up вживую не понадобились ни разу — остаются запасом. [не проверено вживую: запасные приёмы]

## Поле Edit/RichEdit: `EM_REPLACESEL` без фокуса
- **Что:** сообщение вставляет текст вместо выделения в каретку поля, даже если окно не впереди. Номер сообщения < `WM_USER` → строку в чужой процесс переносит сама система.
- **Источники:** [EM_REPLACESEL](https://learn.microsoft.com/en-us/windows/win32/controls/em-replacesel); AutoHotkey `EditPaste` — `SendMessageTimeout(EM_REPLACESEL, TRUE, …, SMTO_ABORTIFHUNG, 2000)` (`source/script_autoit.cpp`).
- **Как в Verba** (`win::replace_sel`): классы `Edit`, `RichEdit20W/A`, `RICHEDIT50W/60W`, `RichEditD2D(PT)`, `WindowsForms10.EDIT.*`, `WindowsForms10.RichEdit*`; `SendMessageTimeoutW` с `SMTO_ABORTIFHUNG`, 1 с; поле только для чтения или выключено — не трогаем; успех — по длине текста поля до и после. Не сработало (UIPI: окно с правами выше — ошибка 5 «отказано в доступе») → переход к перескоку.
- **Проверено:** Блокнот Windows 11 (11.2607, класс `RichEditD2DPT`) — 5 из 5, 0–3 мс; WinForms `TextBox` — 3 из 3; сквозной прогон через Verba — 3 из 3, от отпускания хоткея до вставки 0,91–0,92 с при ответе сервера 0,8 с. Фокус ни разу не тронут.

## UI Automation: первый запрос к Chrome и Electron
- **Что:** Chrome и VS Code включают дерево доступности по первому запросу UIA. Первый `GetFocusedElement` у свежего окна отдаёт `Pane` без своего окна (заглушка документа), а не поле; через ~50 мс — уже поле. Догадка из `research.md` подтвердилась.
- **Как в Verba:** снимок UIA — в отдельном потоке (контроллер не ждёт); элемент `Pane`/`Window` → переспросить через 50 мс, до 6 раз; так и не стал полем → поле опознаётся по окну, как без UIA. Таймауты UIA (`IUIAutomation2`): подключение и запрос — по 1 с. Снимок старше 1,5 с не берётся: человек мог уйти.
- **Замер:** первый снимок свежего Chrome/VS Code — 52–63 мс (с одним повтором), дальше — 0–2 мс. До повтора первый раунд в Chrome проваливался (UIA ждала фокус на «окне»).
- **Источник:** [IUIAutomation2](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomation2) (таймауты).

## Перерисованное поле: протухший RuntimeId
- **Что:** веб-страница пересоздаёт поле (React, смена чата) → старый элемент UIA мёртв: вызовы отвечают `UIA_E_ELEMENTNOTAVAILABLE`.
- **Как в Verba** (`Uia::refind`): ищем в том же окне элемент того же типа — по AutomationId (Chrome отдаёт HTML `id`), иначе по имени, иначе среди фокусируемых по положению; несколько — ближайший к прежней рамке; дальше 32 пикселей суммарного сдвига — не он (кроме единственного совпадения по id/имени).
- **Проверено:** поле пересоздаётся при уходе фокуса — 3 из 3, «найдено заново»; поле удалено — «поле пропало», вставки нет, фокус вернулся (1 из 1).
- **Риск:** чат-приложение, где поле ввода одно на все чаты с одинаковым id, — текст встанет в поле текущего чата, а не того, где начали. [не проверено вживую]

## Перескок: сколько окно впереди
- **Было** 121–130 мс: 100 мс — удержание Ctrl+V (из Handy: некоторые приложения теряли слишком быстрое сочетание, Handy #165).
- **Стало** 31–80 мс: на взводе клавиши отпускаются, как только приложение прочитало буфер (значит, Ctrl+V оно уже обработало), но не дольше 100 мс; ещё 8 мс — чтобы отпускание дошло до окна-цели, а не до человека.
- **Из чего 37 мс** (медиана, Chrome): окно вперёд 2–3 мс → Chrome возвращает фокус на поле ~14 мс → Ctrl+V → чтение буфера 5–20 мс → отпускание + 8 мс → фокус человеку 2–3 мс. Мгновенно нельзя: приложение само должно обработать активацию, нажатие и запросить буфер.
- **Буфер готовится до перескока:** снимок прежнего содержимого и публикация текста — до того, как окно встаёт вперёд (`paste::paste_armed`); Ctrl+V — по команде; команды нет 5 с — буфер возвращается человеку.
- **Замеры** (снаружи, отдельный поток каждые 0,5 мс смотрит, какое окно впереди): Chrome `contenteditable` 10 из 10, 31–46 мс; Chrome `input` 5 из 5, 53–80 мс (читает буфер позже — 8–32 мс); пересозданное поле 3 из 3, 94–118 мс (поиск заново ~70 мс); VS Code 4 из 4, 40–52 мс; сквозной прогон через Verba — 3 из 3, 34–48 мс.

## Пауза в печати человека
- **Что:** нажатия человека за время перескока ушли бы в окно-цель. Перед перескоком ждём 200 мс без клавиш (и без зажатых клавиш и кнопок мыши), не дольше 3 с; паузы нет → не вставляем, уведомление.
- **Почему не `GetLastInputInfo`:** он считает и движение мыши — при живом человеке за ПК раунд провалился «ввод без паузы 3 с», хотя мышь фокусу не мешает. Время последней клавиши берётся у хука и Raw Input (`hook::last_key_tick`).
- **Риск:** человек начал печатать в те же ~40 мс — его буква попадёт в запомненное поле.

## Игры
- **Что:** Ctrl+V в игру с закрытым чатом — нажатия игровых клавиш. В играх у полей нет ID для Windows.
- **Как в Verba:** игра — окно закрывает монитор целиком (кроме развёрнутого окна с рамкой, рабочего стола и панели задач) или exe из `paste.games`. Запомненное окно — игра: впереди — вставка (фокус на месте), не впереди — вставки нет. Впереди сейчас игра — фокус у неё не забираем.
- **Проверено** (форма-«игра» без поля): полноэкранная — 4 из 4 (ушёл — «ты ушёл из игры», на месте — вставка); из списка — 4 из 4. [не проверено вживую: настоящая игра и игра с правами администратора]

## Не используем
- UIA `ValuePattern.SetValue` — заменяет текст поля целиком (решение `research.md`).
- Ввод в фоновое окно (`PostMessage WM_KEYDOWN/WM_PASTE`) — Chrome и Electron так не вставляют, а состояние Ctrl в сообщение не передать.

## Не проверено
- Telegram Desktop, Discord, настоящий Telegram Web — там аккаунты владельца (Telegram ещё и синхронизирует черновики), автоматом не трогали; `contenteditable` в Chrome — их аналог.
- Свёрнутое окно-цель, окно с правами администратора, запасные приёмы foreground lock.
